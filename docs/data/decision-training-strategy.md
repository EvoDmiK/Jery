# Jery 결정 모델 데이터·모델·학습 전략

2026-10-17 공동 검토안. Codex가 통합·계약, Claude가 모델·학습, Antigravity가 데이터·평가를 검토했다. 이 문서는 다음 실험의 설계이며 학습 실행이나 운영 모델 교체를 의미하지 않는다. 최종 교차 검토 상태는 아래 기록에서 확인한다.

## 결정

| 역할 | 모델 / 방식 | 결정 이유와 조건 |
|---|---|---|
| 비교 기준 | 기존 Jery 선형 라우터 | 유지한다. 같은 신규 평가셋에서 모든 비교군과 다시 평가한다. |
| 첫 신경망 후보 | Laya Multilingual 322M, FP16 기반의 기존 결정 헤드 적응 | 가장 작은 실험으로 입력 표현과 판단 학습 가능성을 확인한다. |
| 두 번째 실험 | 같은 Laya의 FP16 기반 + LoRA + 결정 헤드 적응 | 헤드만 학습한 결과보다 개선되는지 검증한다. |
| 조건부 비교군 | Gemma 4 E4B 4비트 기반 + LoRA + 새 Clef 결정 헤드 | 정확한 로더·역전파·저장 경로를 먼저 검증하고 비교한다. |
| 후순위 | Gemma E4B BF16 기반 + LoRA | 첫 실험에서는 진행하지 않는다. 불가능하다고 단정하거나 영구 배제하지 않는다. |

Laya가 더 정확하거나 실제 M4에서 더 빠르다는 결론은 아직 없다. 위 순서는 실패 비용이 작은 실험부터 수행하기 위한 것이다. Gemma의 기존 6건 JSON 생성 시험은 결정 헤드 방식의 성능을 측정한 결과가 아니므로 비교군 탈락 근거로 쓰지 않는다.

설치된 일반 `mlx-lm`의 LoRA 기능과 Unsloth의 결정 헤드 학습 기능은 다르다. 기존 Unsloth MLX 경로를 먼저 확인하고, 맞지 않으면 Laya 공식 MPS 학습 경로를 검토한다. 어느 경로도 이 PC에서 해당 체크포인트의 역전파까지 확인된 상태는 아니다. 새 헤드나 학습 프레임워크를 직접 포팅하는 일은 첫 범위에 넣지 않는다.

## 현재 근거

- 하드웨어: Mac mini M4, 통합 메모리 32GiB.
- 데이터: `mcp-routing-v2`, 카탈로그 `hermes-mcp-57e701d87790`, MCP 5개·도구 96개, 합성 1,162행·340개 시나리오 그룹. train 668 / validation 248 / test 246. 모든 정답은 미검토다.
- 기존 선형 모델의 도구 정확도 82.61%, 결정 정확도 98.37%는 미검토 합성 test 결과다. 새 검토 평가셋의 기준값으로 그대로 사용하지 않는다.
- Claude의 validation 재계산: 선택 정답 232건의 recall@8은 약 97.4%, 원 후보가 96개인 선택 사례 116건에서는 약 94.8%다. 후자의 상위 8개 누락 6건은 모두 Grafana다. 이 계산은 test를 사용하지 않았지만 validation이 기존 모델 설정 선택에 쓰였다는 제한이 있다.
- Laya 옵션 설명에는 기본 256토큰의 별도 예산이 있다. 도구 8개와 세 보조 선택지만으로도 설명이 잘릴 수 있다. Gemma와 Laya의 토큰 수를 서로 대신 사용하지 않는다.
- 원문에 나온 NVIDIA 학습 시간·VRAM 수치는 M4의 예상 측정값으로 사용하지 않는다.

## 입력, 후보와 출력

공개 입력·출력은 [prediction-v1](../contracts/prediction-v1.md)을 유지한다. 입력은 요청, 호출 전 맥락과 후보 명세만 사용하며 정답·ID·분할·검토 상태·출처를 특징에 넣지 않는다. 실제 MCP 실행과 호출 인자 생성은 별도 과제다.

`C`는 사용자가 준 원래 허용 후보, `W`는 모델에 한 번 보여주는 내부 후보 창이다. 선형 순위는 후보를 추리는 데만 사용하며 결정 헤드의 확률과 임의로 곱하지 않는다. 처음에는 `k=8`을 시작점으로 삼고 실제 토큰 예산과 recall을 보고 `k=12`와 비교한다. Claude는 누락 증가 때문에 k=4를 기본 비교군에서 제외할 것을 권고했다. k=4는 필요한 경우 토큰 예산 진단에만 사용한다. 원 후보가 k보다 적으면 그 후보만 사용하며 가짜 도구를 채워 넣지 않는다.

### 내부 질문의 의미

별도 변환 형식 `decision-export-v1`을 설계한다. 기존 v2의 결정과 라벨 의미는 바꾸지 않는다. 내부 질문 `route_in_window`의 선택지는 다음과 같다.

- 현재 창의 도구 alias: 실제 도구 ID와 일대일로 대응.
- `no_tool`: 외부 도구 없이 처리할 요청.
- `clarify`: 요청 자체에 필수 대상·맥락이 빠져 확인할 요청.
- `window_none`: 현재 창에 허용 정답 도구가 없음.

`window_none`은 공개 결정 유형이 아니다. 원래 후보에는 정답이 있지만 내부 창에서 빠진 경우와, 원래 후보 전체로도 지원 불가인 경우를 학습·런타임에서 구분하는 내부 상태다. 이를 즉시 공개 `unsupported`로 바꾸지 않는다.

| 원본 정답과 현재 창 | 내부 학습 정답 | 공개 처리 원칙 |
|---|---|---|
| select_tools, 허용 도구가 W에 있음 | W에 있는 허용 도구 | 선택을 원래 ID로 복원하고 검증 |
| select_tools, 허용 도구가 C에는 있지만 W에 없음 | window_none | 검색 확장·위임; 원본 정답을 unsupported로 변경 금지 |
| 원본 unsupported | window_none | C 전체를 확인한 경로에서만 unsupported 확정 |
| 원본 no_tool / clarify | 같은 결정 | 낮은 확신만으로 clarify 생성 금지 |

단계별 원본 라벨·후보 집합·변환 규칙은 추적용 메타데이터로 보존하고 모델 입력과 분리한다. 후보 누락을 all-zero 학습 타깃이나 거짓 unsupported로 만들지 않는다.

### 추론과 복구

1. C 안에서 선형 순위를 만들고 첫 창을 점수화한다.
2. window_none, 예산 초과, 계약 오류 또는 검증된 수용 기준 미달이면 다음 창으로 확대하거나 원래 에이전트에 C를 전달한다.
3. 초기 파일럿은 복구 창 수를 제한하고 초과하면 위임한다. 전체 순회 방식은 최악 지연을 별도 측정한 뒤 선택한다.
4. 서로 다른 창의 softmax 확률을 비교해 승자를 고르지 않는다. 창별 후보를 다시 한 질문에 모아 평가하거나 위임한다.
5. C 전체를 확인하지 않은 축소 후보 결과만으로 unsupported를 확정하지 않는다. 위임·보류는 런타임 처리이며 공개 계약에 새 결정 유형을 추가하지 않는다.

이 절차가 모든 검색 누락·오판을 방지한다는 뜻은 아니다. 정답 누락 상태에서 다른 도구를 높은 확신으로 고르는 실패도 전체 흐름 평가에 포함한다. 후보 recall, 복구 성공률, 잘못된 거절과 위임 비율을 함께 보고한다.

### 토큰과 action

옵션에는 짧은 alias와 핵심 설명만, state에는 요청·필요한 이전 맥락·alias와 연결된 압축 도구 카드를 넣는다. 요약은 허용된 명세에서만 만들고 정답을 보고 작성하지 않는다. 같은 서버의 비슷한 도구를 구별하는 기능·필수 대상·action 차이는 보존한다.

문자 수를 토큰 수로 가정하지 않는다. 실제 Laya tokenizer로 옵션별 잘림·충돌과 state 잘림을 확인한다. 필요한 정보가 잘리는 사례는 길이를 늘리거나 표현을 바꾸며 조용히 학습에 넣지 않는다. 후보·보조 선택지 순서를 바꿔도 alias와 정답이 함께 대응하도록 검증한다. 필드 순서 셔플과 선택지 순서 셔플을 혼동하지 않는다.

action은 도구 선택이 검증된 뒤 해당 도구의 enum만으로 별도 질문을 구성한다. 첫 공학 파일럿은 도구·결정부터 확인하고 action을 추가한다. 이후 전체 action, 도구를 맞힌 조건부 action, 학습에서 본/못 본 action 지표를 구분한다.

## 데이터 전략

### 첫 단계: 작은 공학 실험

기존 v2 train의 약 32행으로 입력 변환·학습·저장 경로를 검증한다. 기존 validation의 별도 사례로 경계 동작을 확인하되 의미적 품질이나 확률 보정이 검증됐다고 주장하지 않는다. v2에는 독립 보정 분할이 없다. 이 단계에 새로운 실제 로그나 1,000건의 사람 검토를 필수 조건으로 두지 않는다.

### 다음 단계: 검토된 능력 평가용 데이터

향후 목표는 대표 사례 1,000개이며 train 500 / dev 150 / calibration 150 / fresh test 200으로 나눈다. 다음은 수량이 양립하는 목표안이며 현재 구축된 데이터가 아니다.

| 대표 사례 | train | dev | calibration | fresh test | 합계 |
|---|---:|---:|---:|---:|---:|
| select_tools | 384 | 96 | 96 | 96 | 672 |
| no_tool | 38 | 18 | 18 | 34 | 108 |
| clarify | 39 | 18 | 18 | 35 | 110 |
| unsupported | 39 | 18 | 18 | 35 | 110 |
| 합계 | 500 | 150 | 150 | 200 | 1,000 |

도구별 선택 사례는 4/1/1/1개를 목표로 한다. 같은 세션·파생 시나리오의 변형은 한 그룹으로 묶어 같은 분할에 두며, 위 표의 대표 사례 수와 파생 행 수를 따로 기록한다. 문맥 유무 대조쌍도 같은 그룹에 둔다. 실제 그룹 구성과 도구 커버리지에 맞춰 쿼터를 조정하고 결과 manifest로 확인한다.

도구별 최소 수를 맞추면 Grafana 62개 도구의 비중이 커진다. 이와 충돌하는 임의의 서버별 비율 상한을 동시에 강제하지 않는다. 이 표는 운영 트래픽 분포가 아니라 능력 평가용 층화 목표다. fresh test에서 도구별 한 건은 커버리지 확인에 불과하며 도구별 정확도를 입증하기에는 부족하다.

이번 단계는 새로 작성한 시나리오와 검토한 합성 사례로 시작할 수 있다. 실제 Hermes 로그는 후속 단계다. 에이전트끼리 정답에 합의해도 사람 검토 완료로 바꾸지 않는다. 의미 검토와 execution_verified 상태도 분리한다.

우선 보강할 항목:

- 비슷한 Grafana 도구를 구분하는 어려운 후보.
- 비Swallow 서버를 포함한 원 후보에서의 목표 도구 부재.
- 요청 자체의 정보 부족과 모델의 불확실성 구분.
- 같은 요청에서 이전 맥락에 따라 정답이 달라지는 대조쌍.
- 모든 결정 유형에 걸친 후보 개수·위치 변화. 정답을 보존하지 못하는 변형은 생성하지 않는다.
- 새로운 도구·action 명세에 대한 별도 일반화 슬라이스.

v2 원본은 덮어쓰지 않는다. 검토 데이터와 변환 산출물에는 별도 버전·원본 ID·카탈로그 버전·변환 설정·체크섬을 기록한다. 모델 입력에는 이런 메타데이터가 들어가지 않는다.

### 학습용 후보 생성

학습 데이터에 맞춘 선형 모델로 같은 데이터의 후보를 뽑으면 배포 때보다 쉬운 후보가 생긴다. 시나리오 그룹 단위 out-of-fold 순위를 만들어 이 차이를 줄인다. 폴드마다 학습·어휘 통계는 해당 폴드의 학습 그룹에서만 계산한다.

OOF 학습·입력 윈도 생성도 원래 train 안에서만 수행한다. dev·보정·평가에는 실제 후보 생성 결과를 사용한다. 원본 정답을 몰래 후보에 삽입한 결과를 배포 성능으로 보고하지 않는다. OOF에 드는 시간은 별도 측정하며 기존 48개 설정 sweep 시간을 단일 fit 시간으로 가정하지 않는다.

한 요청에서 여러 음성 창을 만들면 window_none 학습량이 과도하게 늘 수 있다. 양성·음성 창의 표집 비율과 요청별 상한, 실제 생성 수를 export manifest에 기록하고 작은 ablation으로 확인한다. 파생 창은 모두 원본 그룹과 같은 분할을 유지한다.

## 학습 설정과 손실

첫 목적 함수는 기존 구현의 supervised soft cross-entropy다. RLCD·강화학습·커스텀 any-of 손실은 첫 범위에 넣지 않는다.

동일 도구의 여러 action이 대안에 있어도 도구 타깃에서는 ID를 먼저 중복 제거한다. 창에 있는 서로 다른 허용 도구에 균등 질량을 줄 수 있다. 이는 동등한 대안을 표현하는 학습 규약이며 사람의 불확실성을 측정한 분포가 아니다. 평가는 top-1이 대안 중 하나인지로 한다. action 타깃은 선택 도구에 해당하는 대안만 사용한다.

Laya 실험 순서:

1. 사전학습된 기존 결정 헤드를 고정된 FP16 본체 위에서 적응시킨다.
2. 헤드 적응과 같은 데이터에서 LoRA를 추가해 비교한다.
3. 시작 rank는 8 또는 16 중 하나로 고정하고 한 번만 비교한다. LoRA 학습률 2e-5와 2e-4는 작은 비교 범위이며, 헤드 학습률은 1e-4를 시작값으로 삼는다. 최적값으로 확정된 수치가 아니다.
4. 마이크로배치 1로 자원을 확인하고, 가능하면 2/4/8로 늘린다. 유효 배치 8~16을 기준으로 epoch당 실제 optimizer update 수를 기록한다. 작은 데이터에서 누적 배치를 과도하게 키우지 않는다.
5. 입력 1,024토큰·헤드 예산 256에서 확인하고 필요한 정보가 잘리면 확대 실험한다. gradient checkpointing을 활용한다.
6. 최대 3개 설정을 dev로 비교하고, 고른 설정만 여러 seed로 재현한다. epoch 상한과 조기 종료는 미리 고정한다. 작은 초기 실험은 1 epoch 후 상태를 확인한다.

백엔드가 지원하지 않는 layers_to_transform·추가 PEFT 옵션을 일반 LoRA 경험만으로 지정하지 않는다. 설치 버전의 실제 설정과 학습 가능한 파라미터 수를 기록한다.

Gemma는 별도 환경에서 4비트 로드·새 헤드·짧은 역전파·저장 복원부터 확인한다. 이미 받은 MLX 폴더를 그대로 사용할 수 있는지, BF16 원본을 거쳐야 하는지, Clef의 Qwen 형식 템플릿이 Gemma에 적합한지는 미확인이다. 모델이 크다는 이유만으로 데이터 문제나 과적합의 해결책으로 사용하지 않는다.

## 보정, 평가와 실험 통과 조건

- train: 모델·전처리·후보 생성 학습.
- dev: 모델·입력 표현·후보 크기 등 설정 선택.
- calibration: 설정을 고정한 뒤 확률 보정·수용 기준 선택.
- fresh test: 모두 고정한 뒤 최종 비교. 이미 살펴본 v2 test는 회귀 확인용으로 구분.

기본 온도 보정도 그대로 신뢰하지 않는다. 대안 정답의 any-of 판정과 soft-target CE는 목적이 다르다. 옵션 분포 보정과 '최종 top-1 선택이 허용 정답인가'에 대한 수용 신뢰도를 구분하고, 정의·표본 수·reliability를 기록한다. 조건부 헤드 보정에 정답이 창에 있는 사례만 쓰면 그 범위를 명시한다. 원 후보 전체 기준 수용/위임 검증에는 검색 누락 사례도 반드시 포함한다.

다른 창·다른 후보 개수에서 얻은 확률을 전역 정답 확률로 간주하지 않는다. 표본이 적은 상태에서 결정별 임계값·복잡한 보정기를 늘리지 않는다. prediction-v1 confidence는 보정된 성공 확률을 보장하는 필드가 아니다.

| 단계 | 필수 확인 |
|---|---|
| 환경 | 패키지·소스·모델 revision 고정, import와 정확한 체크포인트 로드 |
| 입력 | 필드 누출 없음, 옵션 충돌·필수 정보 잘림 없음, alias 역변환·후보/action 검증 |
| 학습 | 작은 train에서 유한 손실·기울기, 손실 감소·학습 정답 일치 상승, 학습 대상 갱신과 고정 본체 보존 확인 |
| 복원 | 저장·재로딩 예측 일치, 어댑터/헤드/기반 모델 결합 재현 |
| 자원 | 대표 긴 입력에서 실제 M4 메모리·step 시간·p50/p95·콜드 로드·복구 최악 지연 측정 |
| 품질 | 동일 검토셋의 선형 기준과 비교, 검색 누락·위임을 포함한 전체 흐름과 단계별 지표 보고 |

품질 지표는 결정별 precision/recall·macro F1, 도구 정확도, action과 joint 정확도, 불필요 호출, 잘못된 unsupported, 후보 recall@k, 복구 성공과 위임 coverage, 보정 오차를 포함한다. 클래스·도구별 표본 수와 시나리오 단위 불확실성도 함께 제시한다. 보류 사례를 제외한 정확도만 보고하지 않는다.

비교 기준은 두 개로 둔다. 현재 저장된 선형 모델은 기존 동작과의 비교에 사용하고, 같은 새 train과 동일한 데이터 사용 정책으로 재학습한 선형 모델은 구조의 이득을 비교하는 기준으로 둔다. 새 모델에만 검토 데이터를 추가한 차이를 모델 구조의 개선으로 보고하지 않는다. 후보 생성기도 해당 실험의 train만 사용한다.

복구 창 상한 때문에 원래 unsupported인 요청이 위임으로 끝날 수 있다. 이 경우 자동 경로의 unsupported recall과 위임 coverage를 따로 보고한다. 위임을 자동 정답으로 계산하지 않으며 위임 이후 결과가 없으면 전체 처리 성공도 미확인으로 남긴다.

첫 실험의 자원 예산과 지연 목표는 probe 후 고정한다. 아직 측정하지 않은 수십 ms·몇 GB·몇 분을 성능 사실이나 운영 채택 기준으로 선언하지 않는다. 새 검토셋에서 선형 대비 이득이 없으면 선형 모델을 유지한다. 운영 적용 전에는 별도 shadow 평가가 필요하다.
